# Проверка безопасности SimpleHash

## Коротко

SimpleHash помогает изучать хеширование, но не предназначен для паролей, подписей или защиты данных. Длинный результат и хорошая статистика сами по себе не делают функцию безопасной. Ниже — результаты запуска финального варианта в Docker с PHP 8.3. Числа времени показывают порядок величины, зависят от машины и входных данных.

| Вопрос | 32 бита | 128 бит |
|---|---|---|
| Коллизия | 🔴 Найдена для двух сообщений | ⚪ Не искали; 2⁶⁴ — только идеальная оценка |
| Прообраз | 🟡 Нашли для сокращённого результата, полный не искали | ⚪ Не искали; 2¹²⁸ — только идеальная оценка |
| Второй прообраз | ⚪ Не искали | ⚪ Не искали |
| Продление хеша | 🟡 Наивная попытка в одном примере не удалась | 🟡 Наивная попытка в одном примере не удалась |
| Обратимость | 🟡 Внутренние операции обратимы; финал неоднозначен | 🟡 Внутренние операции обратимы; выход связывает четыре состояния |

🔴 — показана проблема; 🟡 — результат ограниченного опыта; ⚪ — нет практической проверки. Неудача наивной попытки продления не доказывает, что другие способы не работают.

## Словарь

- **Хеш** — короткий результат вычисления по входу произвольной длины. Здесь вход читается по байтам.
- **Коллизия** — два разных входа с одинаковым хешем.
- **Прообраз** — вход, который даёт заранее заданный хеш.
- **Второй прообраз** — другой вход с тем же хешем, что у заданного сообщения.
- **Парадокс дней рождения** — совпадение среди многих пар может появиться намного раньше, чем совпадение с одним заранее выбранным значением: число пар растёт примерно как квадрат числа участников.
- **Обратимость** — возможность однозначно восстановить вход преобразования по его результату. Например, поворот битов можно отменить поворотом в другую сторону.
- **Обратная связь (feed-forward)** — здесь исходное состояние ещё раз соединяется с результатом преобразования через XOR. Из `A(y) XOR y` нельзя восстановить `y` обращением одного `A`; это само по себе не доказывает криптографическую стойкость.
- **Односторонняя функция** — функция, которую легко вычислить, но для которой трудно найти вход по результату. Трудность для SimpleHash не доказана.
- **Продление хеша (length extension)** — способ получить хеш сообщения с добавленными данными по известному хешу и длине исходного сообщения, не зная всех его байтов. Работает не для каждой конструкции.
- **MAC** — проверочный тег с секретным ключом, позволяющий проверить подлинность сообщения. **HMAC** — стандартный способ построения такого тега с криптографической хеш-функцией; безопасность HMAC с SimpleHash здесь не установлена.
- **Биты стойкости** — масштаб работы в виде степени двойки: например, 64 бита означают порядок 2⁶⁴ операций. Длина выхода не гарантирует столько бит стойкости.

## Масштабы

Шаг 1 измерил на одном устройстве примерно **356 850** 32-битных и **100 633** 128-битных хешей в секунду на входе длиной 12 байт. В таблице число попыток делится на соответствующую скорость; это порядок величины, зависит от машины. Реальный поиск может иметь другую скорость, требовать памяти или допускать более дешёвую атаку.

| Попыток | Примерный смысл для идеального хеша | Время по измеренной скорости |
|---|---|---|
| 2¹⁶ = 65 536 | Масштаб поиска любой 32-битной коллизии | 0,184 с при 32 битах |
| 2³² ≈ 4,29 млрд | Масштаб поиска заданного 32-битного значения | 3,34 часа при 32 битах |
| 2⁶⁴ ≈ 1,84·10¹⁹ | Масштаб поиска любой 128-битной коллизии | 5,81 млн лет при 128 битах |
| 2¹²⁸ ≈ 3,40·10³⁸ | Масштаб поиска заданного 128-битного значения | 1,07·10²⁶ лет при 128 битах |

Это ориентиры для равномерного идеального хеша, а не измеренная стойкость SimpleHash. Например, среднее число попыток до первой случайной 32-битной коллизии точнее оценивается как √(π/2 · 2³²) ≈ 82 137, а не ровно 65 536.

## Эксперимент 1: коллизия (шаг 2)

**Вопрос.** Можно ли найти два разных сообщения с одинаковым 32-битным хешем?

**Идея с аналогией.** Как в комнате с днями рождения, каждое новое значение сравнивается со всеми уже увиденными. Поэтому совпадение любой пары появляется раньше, чем попадание в конкретное заранее выбранное значение.

**Расчёт.** Для идеального 32-битного результата средний ориентир первой коллизии — около 82 137 попыток; для 128 бит масштаб порядка 2⁶⁴.

**Реальный результат.** Среди строк-счётчиков `x63766` и `x127939` получили одинаковый `55a92eae`. Повторная проверка публичным методом подтвердила пару; потребовалось 127 940 попыток и 0,318 с на этой машине.

**Что это значит.** Коллизия 32-битного варианта воспроизведена. 128-битную коллизию не искали; расчёт для идеального хеша не подтверждает стойкость нашей конструкции.

## Эксперимент 2: обратимость (шаг 3)

**Вопрос.** Можно ли развернуть вычисление назад от результата?

**Идея с аналогией.** Отдельные движения можно отменить, как поворот ключа в обратную сторону. Но если два разных исходных состояния дают один финальный результат, по нему одному нельзя узнать, какое из них было исходным.

**Расчёт.** При фиксированном байте раунд обратим; обратим и `avalanche`. В 32-битном финале вычисляется `avalanche(y) XOR y`: обращение одного `avalanche` не возвращает исходное `y`.

**Реальный результат.** Зеркало совпало с публичным API и векторами в 30 из 30 случаев. На 10 000 состояниях раунд и `avalanche` восстановились по 10 000 раз каждый. Для финала найдены два разных состояния `0000930f` и `0000ab82` с результатом `8226e441` за 43 907 попыток.

**Что это значит.** Это коллизия внутренних состояний финала, не пара сообщений. Она показывает потерю однозначности 32-битного финала; перебор и другие атаки остаются возможны. Для 128 бит дорожки связаны смешиванием и обратной связью по состояниям до смешивания; обращение одного финализатора не восстанавливает состояния, но криптографическая односторонность не доказана.

## Эксперимент 3: прообраз (шаг 4)

**Вопрос.** Сколько попыток нужно, чтобы получить заранее выбранное значение?

**Идея с аналогией.** Угадываем номер на замке, но сначала смотрим только на первые несколько разрядов хеша. Это позволяет провести опыт, не ожидая полного перебора.

**Расчёт.** Для идеального независимого результата каждый дополнительный бит примерно удваивает среднее число попыток: ориентиры для 12, 16 и 20 бит — 4 096, 65 536 и 1 048 576. Для полного 32-битного результата — около 2³²; для 128 бит — около 2¹²⁸. Второй прообраз идеального хеша имеет такой же порядок при условии поиска другого входа.

**Реальный результат.** По десяти целям средние составили 2 830,4, 77 270,9 и 1 097 432,8 попытки соответственно. Полные прообразы и вторые прообразы текущей версии не искали.

**Что это значит.** Опыт показывает перебор сокращённого результата, а не доказывает стоимость поиска полного прообраза или второго прообраза. Встреча посередине, требующая пошагового обращения финала, напрямую не применима; другие способы не исключены.

## Эксперимент 4: продолжение токена (шаг 5)

**Вопрос.** Можно ли по токену `H(секрет || сообщение)` и известной общей длине добавить `&admin=1`, не зная секрет?

**Идея с аналогией.** Если итоговый токен раскрывал бы внутреннее состояние счётчика, можно было бы продолжить счёт с этого места. В опыте токен наивно принимается за такое состояние.

**Расчёт.** Тест использует 16-байтный секрет и сообщение `action=read`: общая известная длина 27 байт. Сравнивается предсказанный токен с настоящим после добавления суффикса.

**Реальный результат.** Для 32 бит подделка `ba24937d` отличается от настоящего `12068b4b`. Для 128 бит `55f0dcd96f7092b0ea735d69cce9ea92` отличается от `c4143ee6c6ff1ade4312f6d1578feb36`.

**Что это значит.** Конкретная наивная попытка не удалась для обоих вариантов; другие способы подделки токена не проверялись. Для проверки подлинности на практике применяют HMAC с проверенной криптографической хеш-функцией; безопасность HMAC с SimpleHash не проверялась.

## Что мы не проверяли

- Полные 32- и 128-битные прообразы и второй прообраз текущей версии (для версии до P6 второй прообраз находили, но после смены финала этот результат не переносится); коллизии полного 128-битного выхода.
- Другие способы продолжения, неизвестную длину секрета и реальные протоколы.
- Дифференциальный и линейный анализ, связи между состояниями и полный математический анализ стойкости.
- Четыре дорожки 128-битного варианта при поглощении получают одни и те же байты через один и тот же раунд и различаются только начальными значениями. Позднее они смешиваются, но «настоящая ширина» в 128 бит не доказана.
- Побочные каналы, безопасность паролей и HMAC с этой функцией. Статистические тесты не заменяют криптоанализ.

В криптографических конструкциях используют тщательно исследованные необратимые преобразования и достаточно широкое внутреннее состояние; HMAC решает отдельную задачу проверки подлинности. Ни один из этих приёмов сам по себе не доказывает безопасность произвольной конструкции.

## Как повторить

Из корня проекта каждый шаг запускается в Docker; `N` — одно число от 1 до 6:

```sh
docker compose run --rm app php security.php --step=1
docker compose run --rm app php security.php --step=2
docker compose run --rm app php security.php --step=3
docker compose run --rm app php security.php --step=4
docker compose run --rm app php security.php --step=5
docker compose run --rm app php security.php --step=6
```

Команда `docker compose run --rm app php security.php` запускает все шаги последовательно. Измеренное время и скорость зависят от машины; фиксированные входы и seed позволяют повторить сами примеры.
