# Краткая оценка криптостойкости SimpleCryptoHash

Проверка выполнена 6 ноября 2026 года на текущей реализации
[`src/SimpleCryptoHash.php`](../src/SimpleCryptoHash.php) в Docker с PHP 8.3 CLI.
Алгоритм и эталонные векторы не менялись. Это короткий анализ двух конкретных
сценариев, без большого перебора и без повторения статистических уровней 3–6.

**Вывод:** 32-битный вариант допускает практически мгновенный подбор другого
сообщения под заданный хеш. Для обоих вариантов подтверждено вычисление хеша
продолженного сообщения по хешу и длине исходного. Поэтому схема аутентификации
`H(secret || message)` допускает подделку при известной длине. Стойкость
128-битного варианта к поиску коллизий и прообразов этой проверкой не установлена.
Для паролей, подписей и безопасности функция по-прежнему непригодна.

## Что проверялось

| Сценарий | 32 бита | 128 бит |
|---|---|---|
| Другой вход под заранее заданный хеш | Найден, подтверждён публичным `get()` | Не искался |
| Предсказание `H(M || suffix)` по `H(M)` и длине `M` | Подтверждено | Подтверждено |
| Подделка тега `H(secret || message)` при известной общей длине | Подтверждена | Подтверждена |

Здесь `||` обозначает конкатенацию байтов. Найденная 32-битная пара не является
коллизией 128-битного варианта: его значения для этих сообщений различаются.

## 1. Целевой второй прообраз для 32 бит

Сначала зафиксированы сообщение `Example text` и его хеш `c0bd6183`.
Затем независимо подбиралось другое сообщение с заданным префиксом `forged:`
и пятью управляемыми байтами, чтобы получить именно этот хеш.

| Вход в hex | Длина | `get()` |
|---|---:|---|
| `4578616d706c652074657874` (`Example text`) | 12 байт | `c0bd6183` |
| `666f726765643aebcc043fd8` | 12 байт | `c0bd6183` |

Хеши 128 бит для той же пары:

```text
Example text: a76e8df2bfabc0aa6d319fbb55403207
Другой вход:  4636e68f653c7b53ad6e67f51ce0cfee
```

Применена встреча посередине:

1. По целевому хешу и выбранной длине обращён финализатор, получено требуемое
   состояние после обработки сообщения.
2. После префикса перебраны 65536 вариантов первых двух байтов суффикса;
   промежуточные состояния сохранены в таблице.
3. Из целевого состояния обращены последние три байтовых раунда. На 278489-м
   обратном кандидате найдено состояние из таблицы.
4. Собранный вход проверен исходным публичным методом `get()`.

Успешный прогон занял **0,184 секунды внутри PHP**, без времени запуска
контейнера: 65536 прямых и 278489 обратных кандидатов, 966546 байтовых раундов,
включая обработку префикса. Это измерение одной цели и одного префикса,
а не гарантия такого времени для любой цели. Единица работы здесь — байтовый
раунд, а не полный вызов хеш-функции.

Причина: состояние имеет всего 32 бита, а раунд и финализатор обратимы.
Для обращения использованы собственные обратные константы по модулю 2³²:

```text
0xA7D46BAD⁻¹ = 0x160C3025
0xD59B4E93⁻¹ = 0x4661FF9B
0xA3C79B5D⁻¹ = 0x0FA490F5
```

Для `y = x XOR (x >> k)` обратное преобразование равно
`x = y XOR (y >> k) XOR (y >> 2k) XOR …`, пока сдвиг меньше 32.
Обращение вращения — вращение в другую сторону. Длина подмешивается XOR,
поэтому при известной длине это действие тоже обращается.

Это целевой второй прообраз: исходное сообщение было задано до поиска.
Обычный поиск любой пары совпадающих 32-битных хешей и без анализа конструкции
имеет масштаб порядка 2¹⁶ попыток по парадоксу дней рождения; для заданного
значения идеальный общий перебор имеет масштаб 2³². Это теоретические ориентиры,
а не оценка безопасности нашей реализации. См. разделы 4.1–4.2
[NIST SP 800-107 Rev. 1](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-107r1.pdf).

### Проверка найденной пары

Из корня проекта:

```sh
docker compose run --rm app php -r '
require "autoload.php";
$h = new SimpleHash\SimpleCryptoHash();
$a = "Example text";
$b = hex2bin("666f726765643aebcc043fd8");
echo $h->get($a), PHP_EOL, $h->get($b), PHP_EOL;
exit($a !== $b && $h->get($a) === $h->get($b) ? 0 : 1);
'
```

Ожидаются две строки `c0bd6183` и код возврата `0`. Здесь нулевой код означает
воспроизведённую уязвимость, а не успешную проверку безопасности.

## 2. Предсказание продолжения и подделка тега

В отдельном тесте проверяющий создал 16-байтный тестовый секрет через
`mt_srand(1)` и 16 вызовов `mt_rand(0, 255)`. Сообщение — `action=read`.
Общая длина `secret || message` — 27 байт, добавляемый суффикс — `&admin=1`.

Функция подделывателя получила **только исходный хеш, число 27 и суффикс**.
Байты секрета и сообщения ей не передавались. Для каждого варианта она:

1. Обратила `avalanche()` и XOR длины.
2. Для 128 бит дополнительно обратила перекрёстное смешивание: строки
   преобразований выполнены в обратном порядке, сложения заменены вычитаниями,
   XOR с соседним состоянием повторён.
3. Продолжила байтовые раунды на суффиксе и выполнила обычную финализацию
   с новой длиной 35 байт.

| Метод | Исходный тег | Предсказанный тег после добавления `&admin=1` |
|---|---|---|
| `get()` | `f07b4501` | `0acf3b52` |
| `get128bit()` | `fab6c593ff65c67f239f7b80eedaee9d` | `dcdd8edcda56a04d520bd36402f4bce8` |

Проверяющий независимо вычислил оба тега через исходные публичные методы
на `secret || message || suffix`: **оба предсказания совпали**. После получения
исходных тегов подбор секрета не выполнялся. Известная общая длина — условие
этой демонстрации; сценарий с неизвестной длиной отдельно не проверялся.

Это атака продолжением (length extension). Здесь не нужен даже промежуточный
паддинг: подмешивание длины и все финальные преобразования можно обратить.
Само наличие length extension не доказывает возможность поиска коллизий или
прообразов полного 128-битного хеша. Оно показывает конкретную непригодность
схемы `H(secret || message)` как MAC. Такая проблема встречается и у других
конструкций хеша; HMAC специально учитывает атаки продолжением — см.
[RFC 8152, §9.1](https://www.rfc-editor.org/rfc/rfc8152.html#section-9.1).
Безопасность HMAC с нашей учебной функцией здесь не утверждается и не проверялась.

## Границы выводов

- Для 32 бит получен конкретный целевой второй прообраз, а не только плохая
  статистика распределения или случайная коллизия.
- Для 128 бит подтверждён сценарий подделки тега при известной длине;
  коллизии, прообразы и вторые прообразы полного выхода не искались.
- Идеальный 128-битный выход предполагает общий масштаб порядка 2⁶⁴ для
  поиска любой коллизии, но эта цифра не устанавливает стойкость данного
  алгоритма. Полноценный дифференциальный анализ и поиск связей между четырьмя
  состояниями не выполнялись.
- Не проверялись неизвестная длина секрета, побочные каналы, пароли и реальные
  протоколы. Даже прохождение лавины и χ² не отменяет найденные атаки.

Краткая проверка подтверждает учебное назначение функции. Подбор констант
и увеличение числа раундов финализатора могут улучшать статистику, но сами
по себе не устраняют обратимость финала и описанный сценарий продолжения.
