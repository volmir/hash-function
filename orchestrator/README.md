# Оркестратор заданий для Codex CLI

Автоматически выполняет серию заданий из `TASKS.md` по очереди: на каждое задание — отдельный запуск `codex exec` с моделью по сложности, проверка, запись итога в журнал, коммит и push.

## Как это устроено

```
orchestrator/run.sh        скрипт-оркестратор (обычный bash, токены не тратит)
orchestrator/TASKS.md      15 заданий + метаданные (tier, gate, retries)
orchestrator/PROGRESS.md   журнал итогов = «память» (создаётся скриптом, коммитится)
.orchestrator/             логи и разобранные задания (локально, в git не попадает)
```

Цикл по каждому заданию:

1. Берётся следующее задание, которого ещё нет в `PROGRESS.md` с отметкой ✓.
2. Запускается **новый** `codex exec` (чистый контекст) с `-m <модель по tier>` и `-c model_reasoning_effort=<усилие>`. В промпт добавляются правила, ID и последние 15 строк журнала.
3. Скрипт сам запускает проверку (`gate`) внутри Docker. Если проверка не прошла, агент получает вывод и **одну** попытку исправить (`codex exec resume --last`), затем остановка.
4. В `PROGRESS.md` дописывается строка с итогом агента, затем `git commit` и `git push` в ветку `auto/hash-function`.
5. Следующее задание. При любой ошибке скрипт останавливается, ничего не коммитит и ничего не портит.

Почему оркестратор скриптом, а не ИИ: он не расходует токены, не «забывает» шаги, не раздувает контекст, а коммит и push выполняются вне песочницы Codex (внутри неё сеть выключена, а `.git` защищён от записи).

## Подготовка (один раз)

1. Установите и авторизуйте Codex CLI (`codex --version`, `codex login` либо переменная `CODEX_API_KEY` для `codex exec`).
2. Скопируйте каталог `orchestrator/` в корень проекта. В корне проекта должны быть `AGENTS.md` и `docker-compose.yml` (сервис `app`).
3. Убедитесь, что репозиторий чистый и есть remote `origin` с рабочей авторизацией (SSH-ключ или credential helper) **в той оболочке, из которой запускаете скрипт**.
4. Проверьте флаги вашей версии Codex: `codex exec --help`. Скрипт использует `-m`, `-c`, `--sandbox`, `-o`, подкоманду `resume`. В новых версиях `--full-auto` объявлен устаревшим, а `--ask-for-approval` у `exec` удалён; в скрипте их нет.
5. Узнайте id доступных моделей (в интерактивном `codex` команда `/model`) и задайте три уровня:

```bash
export MODEL_LIGHT="<лёгкая быстрая модель>"      # P1–P4
export MODEL_STANDARD="<основная модель для кода>" # P5, P7–P10, P12–P15
export MODEL_HEAVY="<самая сильная модель>"        # P6, P11
# усилие рассуждения (по умолчанию low / medium / high):
export EFFORT_LIGHT=low EFFORT_STANDARD=medium EFFORT_HEAVY=high
```

Если модель не задана, используется модель Codex по умолчанию (различаться будет только усилие). Уровни заданий меняются строкой `tier:` в `TASKS.md`.

## Запуск

```bash
chmod +x orchestrator/run.sh
orchestrator/run.sh --list                 # таблица заданий и статусов, ничего не запускает
orchestrator/run.sh --only P1 --no-push    # пробный запуск одного задания без push
orchestrator/run.sh                        # весь цикл до конца или до первой ошибки
orchestrator/run.sh --from P6              # начать с P6 (выполненные пропускаются)
```

**Первый раз обязательно** сделайте пробный `--only P1 --no-push` и посмотрите `git show`, лог `.orchestrator/logs/P1.exec.log` и строку в `PROGRESS.md`. Скрипт проверен мной только с заглушкой `codex` (разбор заданий, цикл, повтор через `resume`, коммит/push, остановка при ошибках), с настоящим Codex я его не запускал.

Полезные переменные: `SANDBOX` (по умолчанию `workspace-write`), `GATE_BASE` (как запускать проверки, по умолчанию `docker compose run --rm app`), `BRANCH`, `TASK_TIMEOUT` (секунды на запуск), `NO_PUSH=1`, `CODEX_BIN`.

## Если остановилось

| Сообщение | Что делать |
|---|---|
| «проверка не прошла» | смотрите `.orchestrator/logs/Pn.gate.log`; исправьте вручную или откатите (`git checkout -- . && git clean -fd -e orchestrator`) и запустите заново |
| «чужие изменения в рабочем дереве» | закоммитьте или уберите их |
| «агент изменил защищённые файлы» | откатите `orchestrator/run.sh` и `TASKS.md` из git |
| «агент не изменил ни одного файла» | проверьте `Pn.exec.log`; возможно, модель отказалась или упёрлась в песочницу |
| push не удался | коммиты сохранены локально; выполните `git push -u origin auto/hash-function` |

Задание, которое вы выполнили или дочинили руками, отметьте командой:
`orchestrator/run.sh --mark-done P6` (закоммитит текущие изменения, допишет журнал, сделает push).

Задание **P8** запускается с `retries: 0`: если метрики не проходят пороги, нужно ваше решение (поправить документацию, порог или алгоритм), автоматически агент ничего ослаблять не должен.

Для текущей версии пользователь принял ограничение P8: ровно 238 коллизий
`SimpleHash32` на 1000000 случайных входов при `seed=1`, ожидание ≈116,415,
порог ≈237,83. Результат описан в README проекта; обычный `php run.php`
сохраняет код `1`. Финальная общая проверка находится в **P15**; P14 проверяет
только `security.php`.

Gate P15 сначала проверяет свою логику через `php tests/check-orchestrator.php`,
затем запускает `php orchestrator/check-quality.php`. Эта обёртка выполняет
все уровни Runner с `seed=1` и читает структурированный отчёт. Она принимает
полный успех либо только согласованное отклонение P8 при успехе остальных
измерений нашей функции. Другие числа коллизий, наборы, seed, провалы уровней,
незавершённые измерения и исключения приводят к ошибке. После неё через `&&`
выполняются проверки измерителя, CLI и безопасности; их ошибки не допускаются.
Пороги и статистические выборки не меняются.

Проверка этой логики и обрезания UTF-8:

```sh
docker compose run --rm app php tests/check-orchestrator.php
docker compose run --rm app php orchestrator/check-quality.php
```

Итоги в журнале ограничиваются 300 символами средствами Bash в локали
`C.UTF-8`, независимо от внешнего `LC_ALL`. Русские буквы и эмодзи сохраняются
целиком. Повреждённые прежним обрезанием итоги P6, P7 и P10 восстановлены
из сохранённых `.orchestrator/logs/Pn.last.md`.

## Ограничения и безопасность

- Песочница `workspace-write` по умолчанию без сети и обычно без доступа к Docker: агент **не может** сам прогнать `docker compose`, поэтому проверки запускает скрипт, а в промпте агенту велено писать «не проверено», если он не смог запустить. `danger-full-access` включайте только в изолированной среде (ВМ, контейнер, отдельная ветка).
- Всё идёт в ветку `auto/hash-function`, не в `main`. Просмотрите историю (`git log`, `git diff main..`) и слейте через pull request.
- Не кладите в проект секреты: агент читает весь каталог.
- Расход токенов: уровни `light` и `low` на механических заданиях и новый контекст на каждое задание. «Память» между заданиями это 15 последних строк журнала, а не вся история.
- Журнал и логи содержат итоги агента, а не доказательства: после цикла просмотрите результаты `php run.php`, `php security.php` сами.
- Windows: запускайте из WSL (bash, git, docker доступны там же).

## Запасной вариант: оркестратор внутри Codex

Если нужна именно схема «Codex сам запускает субагентов», см. `ORCHESTRATOR_PROMPT.md`. Она дороже по токенам и менее предсказуема, поэтому не рекомендуется как основная.
