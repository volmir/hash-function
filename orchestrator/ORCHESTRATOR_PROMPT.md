# Запасной вариант: Codex как оркестратор (субагенты)

Используйте, если хотите, чтобы главный сеанс Codex сам запускал субагентов. Основной вариант это `run.sh`: он дешевле и предсказуемее. Что нужно знать заранее:

- Субагенты в Codex запускаются только по явной просьбе в промпте, и каждый тратит свои токены.
- Контекст главного сеанса растёт с каждым заданием (деградация качества при 15 заданиях вероятна).
- Выбор модели при запуске субагента зависит от версии Codex; надёжнее всего заранее описать агентов-«уровни» файлами и проверить на пробном запуске, что модель действительно применилась.
- Для commit/push главному сеансу нужен доступ к сети и записи в `.git`, то есть либо подтверждения, либо `danger-full-access` в изолированной среде.

## 1. Включить субагентов

В `~/.codex/config.toml` (или `.codex/config.toml` проекта; в части версий уже включено по умолчанию):

```toml
[features]
multi_agent = true

[agents]
max_threads = 1   # строго по одному заданию за раз
max_depth = 1     # без вложенных субагентов
```

## 2. Три агента-уровня (`.codex/agents/`)

`.codex/agents/task_light.toml`:
```toml
name = "task_light"
description = "Механические правки: переименования, документация, обновление ссылок"
model = "<MODEL_LIGHT>"
model_reasoning_effort = "low"
sandbox_mode = "workspace-write"
developer_instructions = """
Выполняй ровно одно переданное задание. Следуй AGENTS.md. Не делай git commit/push, не меняй orchestrator/.
Если не можешь запустить проверку, так и напиши («не проверено»).
Итог выводи строго: ИТОГ / ПРОВЕРЕНО / НЕ ПРОВЕРЕНО / ОТКЛОНЕНИЯ.
"""
```
`.codex/agents/task_standard.toml`: то же, `model = "<MODEL_STANDARD>"`, `model_reasoning_effort = "medium"`.
`.codex/agents/task_heavy.toml`: то же, `model = "<MODEL_HEAVY>"`, `model_reasoning_effort = "high"`.

(Подставьте id моделей, доступные вашему аккаунту: команда `/model` в Codex.)

## 3. Промпт для главного сеанса

Запуск: `codex` в корне проекта (интерактивно), затем вставьте:

```
Ты ОРКЕСТРАТОР. Сам задания не выполняешь, код не правишь. Твоя работа: диспетчеризация, проверка, журнал, git.

Источник заданий: orchestrator/TASKS.md (секции «## Pn», поля tier/gate/retries и блок ```prompt```).
Журнал (память): orchestrator/PROGRESS.md, выполненные задания помечены строкой «- [Pn] ✓».

Цикл. Для каждого невыполненного задания по порядку:
1. Запусти РОВНО ОДНОГО субагента: tier light → task_light, standard → task_standard, heavy → task_heavy. Передай ему текст из блока prompt этого задания, ID и последние 15 строк журнала. Явно запрети ему commit/push и правку orchestrator/. Дождись завершения, не запускай других субагентов параллельно.
2. Прочитай ТОЛЬКО итог субагента (ИТОГ/ПРОВЕРЕНО/НЕ ПРОВЕРЕНО). Не читай его diff целиком и не пересказывай код, чтобы не раздувать свой контекст.
3. Запусти проверку из поля gate сам: docker compose run --rm app sh -c "<gate>" (если gate = skip, пропусти). Если проверка не прошла, дай тому же субагенту одну попытку исправить (retries из задания), с последними 80 строками вывода; не ослабляй пороги и векторы ради прохождения. Если снова не прошла, ОСТАНОВИСЬ и сообщи мне.
4. Допиши в orchestrator/PROGRESS.md строку «- [Pn] ✓ <дата> — <название> — <ИТОГ одной строкой> (tier, модель)».
5. git add -A; git commit -m "Pn: <название>"; git push -u origin HEAD (ветка auto/hash-function; на main не коммить).
6. Переходи к следующему заданию.

Правила: порядок строго по файлу; задание P8 (retries: 0) при провале сразу останавливает цикл; никогда не помечай задание выполненным, если проверка не пройдена или не запускалась; в конце выведи таблицу «задание / статус / коммит / что не проверено».
Начни с самого первого невыполненного задания.
```

## 4. Проверка перед полным запуском

Дайте оркестратору только одно задание (допишите в промпт «выполни только P1 и остановись») и убедитесь: (а) субагент реально запущен на нужной модели, (б) главный сеанс не правил код сам, (в) коммит и push сработали.
